# ADR-002: Dependency Inversion и границы абстракций

- **Статус:** принято
- **Проект:** Horror Hunter
- **Дата:** 11 ноября 2026 года

## Контекст

В текущем коде `core` класс `FirstScreen` одновременно:

- читает ввод через LibGDX;
- вызывает доменную логику перемещения охотника;
- управляет камерой;
- рисует сцену;
- создаёт часть своих зависимостей (`HunterState`, `TacticalGrid`, `ShapeRenderer`, `Viewport`).

Для прототипа это допустимо, но по мере появления новых способов ввода, тактического режима, AI, сохранений, генерации карт и других внешних систем такой класс быстро станет точкой сильной связанности.

При этом мы не хотим превращать проект в архитектуру, где каждый доменный класс получает бессмысленный интерфейс только ради формального соблюдения SOLID.

ADR-001 уже фиксирует гексагональную архитектуру и правило, что зависимости направлены к `domain`. Этот ADR уточняет, **где именно использовать Dependency Inversion и где интерфейсы не нужны**.

## Решение

### 1. Зависим от абстракций на границах поведения

Интерфейсы вводим прежде всего там, где один слой или модуль использует возможность, реализация которой находится снаружи и потенциально может быть заменена.

Хорошие кандидаты:

- источник команд игрока (`PlayerCommandSource`);
- генератор карты (`MapGenerator`);
- поиск пути (`Pathfinder`);
- источник случайности (`RandomSource`), если требуется детерминированность и подмена в тестах;
- хранилище сохранений (`SaveRepository`);
- часы/время, если игровая логика когда-либо зависит от внешнего времени;
- другие внешние сервисы или алгоритмы, которые домену нужны как возможность, а не как конкретная библиотека.

Конкретные реализации зависят от интерфейсов, а не наоборот.

Пример:

```text
GdxPlayerCommandSource
        |
        v
PlayerCommandSource
        |
        v
application / game controller
        |
        v
domain
```

### 2. Не создаём интерфейс для каждой доменной сущности

Доменные модели и value objects по умолчанию остаются конкретными классами.

Например, **не нужны** интерфейсы вида:

- `IHunterState`;
- `ITacticalGrid`;
- `IWorldPosition`;
- `ICellCoordinates`.

`HunterState`, `TacticalGrid`, `WorldPosition`, `CellCoordinates` — часть нашей модели игры, а не внешние зависимости.

Интерфейс появляется только при наличии реальной границы или нескольких осмысленных реализаций/стратегий.

### 3. Абстрагируем намерение, а не устройство ввода

Не вводим слишком низкоуровневые абстракции вроде `KeyboardInput`, если игровому слою нужна не клавиатура как устройство, а **намерение игрока**.

Предпочтительное направление:

```text
keyboard / gamepad / touch
          |
          v
LibGDX input adapter
          |
          v
PlayerCommandSource
          |
          v
MoveCommand / AttackCommand / UseItemCommand / ...
```

Это позволяет в будущем подключать клавиатуру, геймпад, Android touch, replay или другой источник команд без изменения игровой логики.

### 4. Screen не является доменом

LibGDX `Screen` отвечает за lifecycle платформенного/графического слоя.

Зависимость `Screen` от LibGDX-классов (`Camera`, `Viewport`, `ShapeRenderer` и т.п.) нормальна и сама по себе не требует интерфейсов.

Однако `Screen` не должен постепенно превращаться в место, где живут:

- игровые правила;
- выбор поведения NPC;
- правила тактического режима;
- алгоритмы поиска пути;
- сохранение состояния;
- генерация мира.

По мере роста функциональности orchestration выносится в отдельный application/game-controller слой.

### 5. Создание зависимостей поднимаем к composition root

Объекты не должны по возможности сами создавать заменяемые внешние зависимости.

Сборку приложения выполняем в верхнем слое (composition root), например в `Main` или отдельном bootstrap/composition-классе.

Пример целевого направления:

```java
public void create() {
    HunterState hunter = ...;
    TacticalGrid grid = ...;
    PlayerCommandSource commands = new GdxPlayerCommandSource();

    setScreen(new FirstScreen(hunter, grid, commands));
}
```

Это не означает, что каждую мелочь нужно внедрять через конструктор с первого дня. Composition root расширяем по мере появления реальных зависимостей.

### 6. Порты принадлежат слою, который формулирует потребность

Если возможность нужна домену, порт объявляется в `domain`.

Если возможность нужна только application-слою, интерфейс не обязан находиться в `domain`.

Например, `PlayerCommandSource` скорее относится к application-слою: домен должен понимать команду/действие, но не обязан знать, откуда она пришла.

Это предотвращает попадание UI/input-концепций в чистую игровую модель.

### 7. Рендеринг абстрагируем только при необходимости

Пока `Screen` непосредственно рисует через LibGDX, отдельный `GameView`/renderer-интерфейс не обязателен.

Абстракцию рендера вводим, когда:

- orchestration начинает смешиваться с большим объёмом графического кода;
- требуется несколько реализаций представления;
- это существенно упрощает тестирование application-слоя.

Не создаём renderer-интерфейсы заранее «на всякий случай».

## Направление зависимостей

Упрощённо:

```text
lwjgl3 / android
        |
        v
LibGDX adapters (input/render)
        |
        v
application / controllers
        |
        v
domain
        ^
        |
external adapters
(pathfinding, generation, persistence, ...)
```

Зависимости направлены к более стабильным правилам. Конкретные библиотеки и платформенные API остаются снаружи.

## Практическое правило

Перед созданием интерфейса задаём вопрос:

> Здесь действительно есть граница поведения/внешняя зависимость, которую полезно заменить или подменить?

Если ответ «нет, это просто наша доменная модель», интерфейс, скорее всего, не нужен.

## Последствия

Плюсы:

- `domain` остаётся независимым от LibGDX и сторонних библиотек;
- ввод, генерацию, pathfinding, persistence и другие внешние механизмы можно заменять;
- application-логика становится проще для тестирования;
- поддерживается Android/desktop без протекания деталей устройства в правила игры;
- уменьшается риск появления монолитных `Screen`-классов.

Цена:

- на реальных границах появляется дополнительный слой интерфейсов и адаптеров;
- требуется следить, чтобы абстракции отражали потребности игры, а не API сторонней библиотеки;
- чрезмерное применение DIP может привести к ненужной сложности, поэтому абстракции вводим только при практической пользе.

## Связь с ADR-001

Этот ADR уточняет [ADR-001: Гексагональная архитектура](ADR-001-hexagonal-architecture.md).

ADR-001 определяет общее направление зависимостей и разделение `domain` / adapters. ADR-002 определяет правило применения Dependency Inversion внутри этих границ: **порты для поведения и внешних зависимостей, конкретные классы для собственной доменной модели по умолчанию**.
